# 모수 근거의 적용 범위와 문서 버전

추가 encoder 학습은 **문서의 적용 범위를 일반적으로 구분하는 능력을 개선하지 못했다**. 인위적인 표식이 있는 변형 문서에서는 금액 오류가 1,941개에서 0개로 줄었지만, 같은 문서의 다른 SKU·기간을 정상 형식으로 바꾸자 후보의 오류가 기존 모델보다 많았다. 원래 Dev의 순차 발주·공개 문서 성능도 일부 낮아져 **현재 모델은 교체하지 않았다**. 쉬운 표식을 제거한 자료 생성 규칙과 checkpoint 선택 결함을 수정했으며, 이 수정으로 다시 학습한 결과는 아직 없다.

## Train 문서 변형 진단

실제 Train 입력에서 경제 모수 네 개가 관측되는 출처 49개를 골랐다. 출처마다 모델이 보는 입력 hash로 한 상태를 선택하고, 아래 8개 조건을 고정한 뒤 현재 선택 모델을 L40S에서 실행했다. 총 392개 상태이며, 각 조건은 `c/p/v/b` 196개 필드다. 숨겨진 응답 확률·미래 결과·Test 정답은 사용하지 않았다.

| 조건 | 최종 금액 오류 | 그중 잘못된 금액 승인 | 그중 값 미확정 |
| --- | ---: | ---: | ---: |
| 원래 입력 | 0 | 0 | 0 |
| 화폐 금액을 같은 배율로 변경 | 0 | 0 | 0 |
| 문서 ID와 순서 변경 | 0 | 0 | 0 |
| 포장 수량을 17개로 변경하고 단가 유지 | 0 | 0 | 0 |
| 수수료를 환급액보다 먼저 기재 | 9 | 0 | 9 |
| 다른 SKU의 금액 문서 추가 | 79 | 0 | 79 |
| 다른 기간의 금액 문서 추가 | 80 | 0 | 80 |
| 같은 SKU·기간의 구버전 문서 추가 | 90 | 47 | 43 |

392개 상태 모두 읽지 않은 문서 chunk는 0개였다. 따라서 이 진단의 오류는 원문을 가져오지 못한 결과로 설명되지 않는다. 다른 SKU·기간을 선택한 오류는 기존 검증기가 금액 승인을 막았다. 구버전의 잘못된 금액 47개는 승인돼, 원문 존재와 올바른 적용 근거를 구분해야 함을 보여준다.

수수료 순서 오류 9개에서는 환급액과 수수료가 같아, 피연산자를 거꾸로 선택해도 계산값 0은 맞았다. 하지만 근거의 연산 순서가 잘못돼 검증에서 거부됐다. 숫자 정답만 보면 이 오류를 놓친다. 단일 모델의 통제된 Train 진단이며 실제 조직 문서 성능으로 해석하지 않는다.

## 추가 학습 자료와 분리

자료 생성기는 현재 관측한 초기 Train 문서만 읽는다. 다른 SKU·기간, 구버전·신버전, 환급액·수수료 순서의 다섯 조건을 만든다. 신버전 조건에서는 정답 금액도 바뀌므로, 새 문서를 항상 무시하는 방식으로 풀 수 없다. 모든 문서의 ID를 무작위 식별자로 바꾸고 순서도 섞는다. 빈 모수에 숨겨진 정답을 넣거나 매니저의 응답을 만들어 붙이지 않는다.

그러나 실제 학습한 v1 자료에는 결함이 있었다. 다른 기간에 `other-period-...`를 사용했고, retail의 원래 SKU는 `retail:...`인 반면 다른 SKU는 `SKU-...`로 만들었다. 이런 표식만으로도 문서를 제외할 수 있어, 과제의 SKU·기간과 문서의 적용 조건을 대조하는 학습을 보장하지 못한다. v1의 정확한 생성 소스와 자료는 아래 원시 묶음에 보존했다.

기존 Train 출처를 78개 적합/19개 비교로 나눴다. 추가 예시는 각각 6,051개/1,259개다. 비교 출처의 변형 예시는 학습에서 제외하며, 원래 비변형 Train 자료는 기존 학습에 계속 포함된다. 따라서 이 분할은 **추가 변형 학습의 출처 분리**이고, 모델이 처음 보는 독립적인 출처 Test가 아니다.

[L40S 설정](../configs/l40s-research-parameter-contrasts-v1.json)은 현재 선택 모델에서 encoder까지 2 epochs 추가 학습한다. 실제 응답 상태 replay와 원래 공개 주석을 함께 유지하며, 혼합 후 epoch당 11,920개 사례다. 수요 GRU는 고정하고 추가 행동 가치 학습은 하지 않는다. 원래 Dev 입력·정답·언어 사례가 이전 실행과 같고, 비교용 변형 사례가 실제 학습 목록에 없음을 확인했다.

선택된 checkpoint와 선택 전에 마지막으로 학습된 후보를 구분한다. 원래 Dev의 순차 발주·질문·근거와 공개 문서 결과를 유지하는지 확인하며, 변형 사례의 정확도만으로 현재 모델을 교체하지 않는다. 기존 Test와 새 판매 출처 27개의 고정 평가는 이번 학습·선택에 사용하지 않는다.

## L40S에서 측정한 결과

encoder tensor 134개·projection 2개·fusion 36개·상태 head 4개가 실제 갱신됐고 수요 GRU는 그대로였다. 모델 크기나 추론 구조를 추가하지 않았다. 학습·원래 Dev 평가에 1,038.91초, 최대 GPU 할당 26.02 GiB가 들었다. 아래 변형 비교는 별도 78.33초이며, 같은 가중치와 추론 설정인 마지막 후보의 중복 예측은 재사용했다.

| 변형 학습에서 제외한 Train 출처 19개 | 부모 | 2 epochs 후보 |
| --- | ---: | ---: |
| 모수 금액 오류 / 5,036개 필드 | 1,941 | 0 |
| 모수 상태 오류 / 5,036개 필드 | 1,191 | 0 |
| 근거 오류 / 관측 값 3,808개 | 1,941 | 0 |
| 원문을 모두 읽지 못한 상태 / 1,259개 | 0 | 0 |

다섯 조건 모두 오류가 0개였지만, 후속 진단에서 이 결과가 자료의 형식에 의존함을 확인했다. 이를 문서 적용 범위 판단의 일반적인 개선으로 해석하지 않는다. 출처 수는 19개이며, 이미 원래 Train으로 학습한 출처이므로 독립적인 모델 효과성이나 실제 조직 성능도 입증하지 않는다.

### 정상 형식으로 바꾼 후속 진단

같은 비교용 Train 출처에서 다른 SKU·기간 조건 552개 상태를 선택했다. 다른 SKU를 원래와 같은 형식으로 만들고, 다른 기간을 길이가 같은 실제 날짜 구간 또는 통상적인 상대 기간으로 바꿨다. 그 외 문서·금액·정답 상태·유형·근거·연산은 같음을 검사했다. 추가 학습과 Test 사용 없이 같은 두 checkpoint를 L40S에서 37.79초 동안 비교했다.

| 정상 형식 조건 | 부모 금액 오류 | 2 epochs 후보 금액 오류 |
| --- | ---: | ---: |
| 다른 SKU / 1,104개 필드 | 374 | 630 |
| 다른 기간 / 1,104개 필드 | 352 | 820 |
| 합계 / 2,208개 필드 | **726** | **1,450** |

모든 문서 chunk를 읽었으며, 두 모델의 근거 오류 수도 각각 726개·1,450개였다. 앞선 0개 오류는 쉬운 표식이 있는 조건에 한정된다. 이 후속 진단 역시 이미 사용한 비교용 Train 출처이며, 새 독립 평가 집단은 아니다.

토큰화도 별도로 확인했다. 552개 중 420개는 각 문서 앞에 반복하는 128-token query에서 과제의 SKU·기간이 잘렸다. **완전한 요청은 별도 source로 모델에 제공된다.** 따라서 모델이 적용 범위를 전혀 받지 못했다는 뜻은 아니며, 이 잘림이 오류를 일으킨 정도도 아직 분리 측정하지 않았다.

[현재 생성기](../scripts/prepare_parameter_contrasts.py)와 [v2 설정](../configs/parameter-contrasts-v2.json)은 일반적인 SKU·날짜 형식을 쓰도록 수정했다. 출처 분리를 유지한 적합 6,051개·비교 1,259개를 다시 준비했고, 형식·관측 금액·누락 상태·숨겨진 정답 독립성을 검사했다. **v2는 자료 준비만 완료됐고 학습 효과는 측정하지 않았다.** 현재 생성기는 v2 설정만 받으며, 과거 v1을 재현하려면 v1 묶음의 소스를 사용해야 한다.

| 원래 Dev의 유지 지표 | 부모 | 2 epochs 후보 |

| 생성 60사례 평균 총손실 | 147.6813 | 150.8032 |
| 생성 최종 모수 오류 / 240개 필드 | 0 | 1 |
| 생성 이미 해결된 필드에 대한 요청 | 0 | 3 |

판매의 추가 중단 6개는 품절을 포함한 기간에 있었다. 완전 관측 고유 기간 5개 × 조건 7개의 총손실만 보면 이 악화를 놓친다. 판매 고정 질문 정책은 336건을 모두 회복했다. 생성·판매의 잘못된 발주 진행은 여전히 0건이지만, 필요한 질문·회복과 공개 문서 유지 기준을 충족하지 못했다. 따라서 전체 성능 향상이나 채택 성공으로 보고하지 않는다.

## 확인한 checkpoint 선택 결함과 수정

원래 선택 코드는 모수·상태·유형·근거 지표의 최솟값과 합을 비교했다. 이번 실행의 고정 Dev 모수 구성 792개 상태에서 첫 epoch는 금액·근거 오류 0개와 상태 오류 7개였으나, 두 번째는 금액·근거 오류 각각 3개와 상태 오류 4개였다. 상태 점수의 개선이 금액·근거 하락을 상쇄해 두 번째가 선택됐다.

[선택 코드](../src/newsvendor/structured_train.py)는 이제 이 네 지표 중 하나라도 이미 선택한 후보보다 낮아지면 교체를 거부하고, 거부 이유를 기록한다. 중간 검증·epoch 끝 검증·checkpoint 재개에 같은 기준을 적용한다. 실제 두 epoch의 지표를 사용하는 회귀 테스트는 첫 후보를 유지하고, 재개 후에도 해당 가중치를 복원하는지 확인한다.

이 수정 후 전체 encoder를 다시 학습한 결과는 아직 없다. 기록된 지표에 새 선택 기준을 적용하면 첫 epoch를 선택한다는 것은 **기준의 반사실 검증**이다. 첫 epoch의 순차 발주·공개 문서 성능이 보장된다는 의미가 아니며, 위 표는 수정 전 실제 선택된 두 번째 후보의 측정이다. 현재 선택 모델은 계속 `forecast-v1`이다.

[v1 측정·분리·선택 기준 검증](evidence/research-parameter-contrasts-results.json)과 [v1 원시 입력·예측·실행 소스](evidence/artifacts/research-parameter-contrasts.tar.xz)를 공개한다. 후속 결과는 [정상 형식 진단·v2 준비·검사 기록](evidence/research-parameter-format-results.json)과 [원시 자료·소스 묶음](evidence/artifacts/research-parameter-format.tar.xz)에 별도로 보존한다. 전체 checkpoint·optimizer는 로컬 압축 archive에 모두 보존했고, 선택/common checkpoint는 직접 읽을 수 있게 남겼다. 공개 묶음에 전체 ModernBERT 가중치는 포함하지 않았다. 최종 검사는 테스트 273개, 출처·입력 분리 검사 4종, 수치 smoke 30개 통과다.
