# 숫자 상태 보정과 재학습 안정성

**새 가치 head는 채택하지 않았다.** 매니저 무응답 뒤의 질문 비용은 일부 줄었지만, 평상시 필요한 질문까지 생략해 생성 Dev 총손실이 늘었다. 선택 모델은 `forecast-v1`이다. Test와 별도 27개 출처 holdout은 사용하지 않았다.

## 무엇을 바꿔 비교했나

[이전 표집 실험](recovery-sampling.md)은 내부 검증의 개선이 전체 Train 재학습 뒤 사라졌다. 먼저 저장된 batch 순서를 그대로 재실행했다. 세 seed 모두 선택 시점과 마지막 시점의 가중치 hash가 원래 기록과 정확히 같았다. 판매 실패 상태 6개에서 선택 시점에는 보류가 모두 0건이었지만, 760번 갱신한 마지막 시점에는 5·5·6건이었다. 중간에도 보류 판단이 생겼다가 사라졌다. 단순히 그 상태를 학습할 수 없거나 항상 학습량이 부족한 문제로 설명하기 어렵다. 마지막 시점을 새 후보로 채택하지는 않았다.

기존 head의 Tanh 활성값은 많이 포화되어 있었다. 이를 원인으로 단정하지 않고, **기존 head를 고정한 채 숫자 상태로 행동 점수를 보정하는 작은 경로**를 비교했다. 94차원 숫자 입력에 `94 → 128 → 2` head를 붙이고 마지막 층을 0으로 초기화했다. 처음에는 기존 점수와 같고, 새로 학습하는 파라미터는 12,418개다. ModernBERT·모수 구성기·수요 GRU는 바꾸지 않았다. 입력 전달 경로와 학습 대상이 함께 달라지므로 Tanh 포화의 단일 원인 실험은 아니다.

자료와 학습량은 이전 비교와 맞췄다. 관측한 Train 상태 1,204개, 실제 후속 경로 표적 11,044개, 같은 batch 순서와 optimizer 설정을 사용했다. 68개 family의 928개 상태로 적합하고 17개 family의 276개 상태로 epoch를 선택했다. 부모 encoder는 이 Train 출처를 이미 보았으므로 독립 일반화 평가가 아니다.

세 seed의 내부 선택 epoch는 12·13·13이었다. 내부 표적 손실은 모두 0.194518 → 0.194440으로 낮아졌다. 전체 Train을 40 epochs 재학습한 기록에서 사전에 고정한 같은 epoch의 checkpoint를 사용하면, seed 42·43은 이 점수를 유지했지만 44는 0.194831로 돌아갔다. 따라서 **처음 등록한 재학습 보존 기준은 실패**했다. 이 점수는 이전 정책의 후속 경로로 만든 표적 점수이며 새 정책의 실제 총손실과 구분한다.

## 실패한 기준과 후속 탐색을 구분한다

별도 등록한 Train 순차 비교에서는 내부 선택 head를 그대로 쓰는 조건과 전체 재학습 조건을 평가했다. 원래 Train 514사례·85개 family에 새로운 응답 표본 4개를 적용하고, 판매의 무누락 조건도 추가했다. 같은 모수 채널에는 질문 순서와 관계없이 같은 응답을 제공했다. 부모와 여섯 후보의 총 15,470개 경로다.

| Seed | 전체 재학습: 생성 총손실 | 내부 선택 유지: 생성 총손실 |
| --- | ---: | ---: |
| 42 | 125.4405 | 125.4815 |
| 43 | 124.6637 | 126.3662 |
| 44 | 124.6873 | 125.4405 |

부모의 생성 총손실은 132.8117이었다. 여섯 후보 모두 부모보다 낮았지만, 내부 선택 유지 조건은 세 seed 모두 해당 전체 재학습보다 높았다. 따라서 **내부 선택 유지 방식의 비교 기준도 실패**했다. 부모 대비 실제 총손실 개선과 앞선 표적·선택 방식 기준은 서로 다른 판단이다.

이 불일치를 확인한 후 별도의 **탐색적 Dev 실행**을 등록했다. 앞의 실패를 통과로 바꾸지 않았다. Dev를 보기 전에 주 조건을 전체 재학습, 대표 seed를 42로 고정하고 세 seed 모두 기준을 충족하도록 했다. 내부 선택 유지 조건은 진단용이며, Dev에서 더 좋아 보이는 방식이나 seed로 바꾸지 않기로 했다. 이 Dev 실행을 앞선 프로토콜을 통과한 확증 평가로 표현하지 않는다.

## Dev에서는 정상 질문의 퇴행을 확인했다

원래 생성 Dev 60사례·12개 family와 판매 Dev 336조건을 사용했다. 판매는 네 모수 채널의 응답 유무 16개 조합을 모두 실행했다. 여섯 후보의 총 32,616개 경로다.

| Dev 지표 | 유지 중인 모델 | 전체 재학습 42·43 | 전체 재학습 44 |
| --- | ---: | ---: | ---: |
| 생성 총손실 | 147.6813 | 148.3549 | 148.3549 |
| 판매 총손실, 누락 0% | 24.3925 | 24.3925 | 24.3925 |
| 판매 총손실, 누락 10% | 71.9563 | 71.7439 | 71.9563 |
| 판매 총손실, 누락 20% | 118.1415 | 117.7167 | 118.1415 |

내부 선택 유지 조건은 세 seed 모두 전체 재학습 42·43과 같은 표의 수치였다. 판매의 종료 손실은 유지되었고 질문 비용만 줄었다. 정확한 판매 손실의 분모는 여전히 **완전 관측 5개 기간·4개 출처의 35조건**이다. 전체 336조건의 요청 비용 평균과 이 35조건의 총손실을 직접 더하거나 빼지 않는다. 공개 문서 258사례의 출력과 모수·상태·근거, 무누락 조건의 필요한 요청·회복은 유지됐다. 잘못된 발주 진행과 이미 해결된 모수의 재질문도 늘지 않았다.

그러나 모든 후보가 생성 손실 비퇴행 기준에 실패했다. 전체 재학습 44는 정확한 판매 총손실도 개선하지 못했다. **작은 판매 이익으로 생성 손실 증가를 상쇄했다고 선언하지 않고 모두 기각했다.**

저장된 경로를 대조하면 생성 손실 증가는 한 사례에서 발생했다. 같은 입력과 구성 상태에서 부모는 부족 비용 `b`를 질문한 뒤 발주했고, 새 head는 바로 발주했다. 질문 비용 6.375를 절약하는 대신 종료 손실 46.7910이 발생했다. 사례당 차이 40.4160을 60사례로 나누면 평균 증가 0.6736이다. 질문 이력이 없는 초기 상태여서, 회복을 위한 전역 보정이 평상시 판단까지 바꾼 경우다. 기존 minimax 허용 기준 안의 발주였으므로 이를 금지된 발주로 다시 분류하지 않는다.

계산 방식의 영향도 별도로 확인했다. 학습하지 않은 부모를 native BF16, 행동 head만 FP32, 숫자 입력 열을 0으로 붙인 FP32의 세 조건으로 실행했다. 생성 Dev 60사례씩 총 180개 경로의 행동·발주량·손실이 모두 같았고 평균은 147.6813이었다. 따라서 이번 퇴행은 정밀도·입력 크기 변경만으로 발생하지 않았다. 이 Dev 사례를 학습 표적으로 쓰지는 않았다. 다음 Train 검사는 관측된 응답 실패에서만 보정을 적용하면서 평상시 판단을 보존할 수 있는지에 집중할 수 있다.

## 검증과 공개 재현

[학습 등록](../configs/research-recovery-residual-v1.json) · [Train 순차 비교 등록](../configs/research-recovery-selected-sequential-v1.json) · [탐색적 Dev 등록](../configs/research-recovery-residual-dev-v1.json) · [학습 코드](../scripts/study_recovery_residual.py) · [전체 결과·실패 기준·검증·hash](evidence/research-recovery-stability-results.json)

L40S 소요 시간은 기존 학습 재실행 79.11초, 새 head 학습 185.75초, Train 순차 비교 316.37초, Dev 평가 675.90초, 정밀도 진단 16.32초였다. 구성 상태를 공유한 실험 시간이며 운영 지연으로 해석하지 않는다.

테스트 330개, Ruff, 다섯 자료 버전의 출처 분리 검사, 수치 smoke 30개를 통과했다. 학습 여섯 실행의 batch·출처 분할·선택 epoch·고정 prior·가중치 hash를 검증했고, Train·Dev 48,086개 원시 경로의 입력·비용 합계·보고 지표를 전수 대조했다. [학습·checkpoint·optimizer·실행 소스](evidence/artifacts/recovery-stability-records-v1.tar.xz)와 [원시 경로 48,266개](evidence/artifacts/recovery-stability-rollouts-v1.tar.xz)를 보존한다. 후자는 별도 정밀도 진단 180개도 포함한다. 원래 gzip hash와 압축을 푼 JSON 바이트 hash를 함께 남기며 기록 순서는 바꾸지 않았다.

학습의 입력 cache와 11,044개 원래 표적 경로는 [이전 공개 기록](recovery-replay.md), 비교 batch와 초기 후보는 [표집 실험 기록](recovery-sampling.md)에 있다. 아래 명령은 공개 base bundle과 이번 후보 head로 고정 간격의 Dev 사례를 재현한다. 전체 학습을 새로 수행하는 명령은 아니다.

```bash
tar -xJf docs/evidence/artifacts/recovery-stability-records-v1.tar.xz \
  --wildcards 'results/l40s-recovery-residual-v1/*' \
  'results/l40s-recovery-residual-dev-v1/*'
tar -xJf docs/evidence/artifacts/recovery-stability-rollouts-v1.tar.xz \
  --wildcards 'results/l40s-recovery-residual-dev-v1/*'

CUDA_VISIBLE_DEVICES=GPU-674d64b8-4bdf-7006-1791-5dc7f7245409 \
CUBLAS_WORKSPACE_CONFIG=:4096:8 HF_HUB_OFFLINE=1 PYTHONPATH=src \
.venv-l40s/bin/python docs/evidence/scripts/reproduce-recovery-residual.py \
  --bundle /path/to/forecast-v1 \
  --refit results/l40s-recovery-residual-v1 \
  --dev results/l40s-recovery-residual-dev-v1 \
  --output results/reproduced-recovery-residual.json
```

[공개 base bundle 준비](model-bundle.md)가 필요하며 GPU UUID는 실제 L40S에 맞춘다. 통제 생성 문서·응답의 결과를 실제 조직 업무의 효과로 해석하지 않는다. 공개 숫자 추출, 수요 calibration, 기존 Test 240.35 미만 기준은 아직 해결되지 않았다.

공개 파일 61개를 빈 디렉터리에 복원하고 원래 작업용 데이터·checkpoint·네트워크 접근을 차단해 확인했다. 고정 간격으로 고른 생성 8사례와 판매 7사례의 16가지 응답 조건을 여섯 head로 실행한 **720개 경로의 행동·발주량·손실이 정확히 일치**했다. L40S 실행은 47.60초였다. 결과 재현이며 새로운 선택이나 효과 평가가 아니다. [복원·접근 차단·실제 실행 기록](evidence/artifacts/recovery-stability-reproduction-v1.tar.xz)
