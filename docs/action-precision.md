# 행동 가치 학습과 추론의 정밀도 일치

`encoder.actionPrecision="float32"` 옵션을 추가했다. 작은 가치·회복 head가 학습과 추론에서 같은 FP32 계산을 사용하고, 현재 모수의 수치 입력을 BF16으로 줄이기 전에 받는다. encoder·상태 결합의 BF16 연산과 가중치, 전체 파라미터 수는 그대로다. **이는 수치 일관성 수정이며 정책 성능 향상을 뜻하지 않는다.**

## 실제 L40S에서 확인한 차이

기존 critic 학습은 저장한 토큰 표현을 재사용해 행동 head만 FP32로 학습한다. 실제 모델 추론에서는 encoder부터 행동 head까지 BF16 autocast 안에서 실행됐다. 수치 입력도 행동 표현의 BF16 dtype으로 만들어졌으므로, 정규화된 값 0.500과 0.501처럼 서로 다른 숫자가 같은 값으로 반올림될 수 있었다.

이전 실행에서 저장한 **Train 자기 상태 928개**를 실제 L40S에서 재생했다. 선택된 부모와 실제로 학습됐지만 채택되지 않은 후보의 가중치를 사용했다. 숨긴 정답이나 Dev·Test로 상태를 구성하지 않았다.

| 같은 Train 상태의 비교 | 선택 부모 | 학습 후보 |
| --- | ---: | ---: |
| 기존 추론과 cached FP32 값의 최대 차이 | 0.0009650 | 0.0012636 |
| 그 계산 차이로 다른 행동을 고른 상태 | 0/928 | 1/928 |
| 수정 후 실제 추론과 cached FP32 값의 최대 차이 | 0 | 0 |

값의 단위는 공개 보류 비용으로 정규화한 손실이다. 기존에는 928개 상태 모두에서 수치 입력에 반올림이 있었고 최대 차이는 0.0074565였다. 수정 후에는 입력 수치와 가치·회복 출력이 모두 FP32 학습 계산과 정확히 같았다. 첫 256개 토큰·상태 표현도 이전 GPU 실행과 모든 상태에서 일치했다. 부모의 행동은 그대로였고 후보의 행동만 한 상태에서 달라졌다. 이 한 건으로 기존 성능 정체의 주원인을 설명하지 않는다.

## 구현과 검증 범위

새 옵션은 수치 입력을 이어 붙이기 전에 행동 표현을 FP32로 바꾸고, 가치·회복 head에서만 autocast를 끈다. 학습 가능한 가중치를 추가하지 않는다. 옵션이 없는 과거 설정은 기존 계산을 유지하므로 당시 결과는 당시 소스·설정으로 재현한다.

수치 입력 켜기/끄기와 batch fusion 두 경로에서, 다른 head는 BF16을 사용하면서 행동 head의 출력은 cached 학습과 일치하는지 검사했다. 반올림되던 작은 수치 차이를 보존하고, gradient가 새 입력 열과 encoder까지 전달되는지도 확인했다. 전체 **217개 테스트, Ruff, 세 자료 버전의 출처·입력 분리 검사와 30개 수치 smoke**가 통과했다.

[실제 GPU 검사·버전·hash](evidence/research-action-precision-checks.json), [원시 Train 계산과 검사 코드](evidence/artifacts/action-precision-checks.tar.xz), [고정 소스](evidence/artifacts/action-precision-source.tar.gz)를 보존한다. 첫 GPU 식별 검사에서는 Torch UUID의 `GPU-` 접두사 표기 차이 때문에 실행을 거부했다. 접두사 처리만 바로잡은 뒤 같은 지정 L40S에서 수행했으며 실패 로그도 보존했다.

## 정책 비교의 범위

같은 replay-v1 부모에서 다음 세 조건을 seed 42로 비교했다. Train/Dev와 모델 구성기·GRU 가중치, 두 번의 실제 rollout 수집, 반복당 최대 40 epochs, 학습률·batch 크기·조기 종료·Dev 선택 기준이 같다.

- `control`: 기존 토큰 입력과 FP32 행동 head.
- `value`: 수치 상태 입력과 FP32 행동 가치 head.
- `no_value`: 같은 수치 입력·정밀도에서 질문·회복 분류만 학습.

각 실행은 초기 정책을 정확한 결과가 있는 Dev 95사례에서 평가하고, 최종 정책은 Retail 336사례와 원래 생성 60사례 전체에서 평가한다. 원래 생성·Retail의 `총손실 / 공개 보류 비용` 평균에 동일 가중치를 주어 선택한다. 모수·근거 정확도, 불필요한 질문, 잘못된 발주 진행과 원래 단위의 손실을 함께 확인한다. [사전 설정](../configs/l40s-research-precision-v1-value.json)

이 비교에서 Test를 평가하거나 선택에 사용하지 않는다. 생성 Dev는 12개 독립 family이고, Retail의 정확한 손실은 고유 완전 관측 기간 5개 × 통제 조건 7개에 한정된다. 실제 조직 효과나 수요분포 calibration의 개선으로 일반화하지 않는다.

## 완료한 비교 결과

| FP32 행동 head 조건 | 생성 Dev 평균 총손실 | Retail 평균 총손실 | 학습·평가 시간 |
| --- | ---: | ---: | ---: |
| 토큰 입력 대조군 | 147.6813 | 44.3274 | 347.20초 |
| 수치 상태 입력 | 147.6813 | 44.3274 | 355.02초 |
| 수치 입력 + `no_value` | 181.6758 | 44.3274 | 266.07초 |

세 조건은 각각 이전 BF16 비교와 같은 손실이었다. 두 가치 조건은 새 가중치를 채택하지 않고 초기 부모를 유지했다. `no_value`는 첫 반복 10 epochs의 회복 head를 선택했다. 잘못된 발주 진행과 Retail 불필요한 요청은 모두 0건이었다. 문서 구성기·GRU 가중치, 수치 입력 전후의 초기 Dev 행동, 첫 반복의 Train 표적도 같았다. **새로운 정책 개선을 입증하지 못했으므로 기존 선택 모델을 유지한다.** [전체 결과·선택 이력·가중치 검사](evidence/research-action-precision-results.json)

실행 시간이 이전 보고서보다 짧아진 것을 FP32의 속도 향상으로 해석하지 않는다. 이번에는 초기 전체 Dev 평가를 생략하고 학습기 내부의 초기 Dev 95사례 평가만 수행했으므로 전체 작업량이 다르다. 세 조건 내부에서는 같은 평가 범위를 사용했다.

추가 Train 감사에서는 두 가치 조건의 반복 1·2가 정확히 같은 928개 표적을 사용한 것을 확인했다. 고정 응답 hash와 초기 정책 복원 때문에 같은 응답 표본을 다시 수집했다. Train의 추가 응답 잡음은 0.1, Dev는 0이고, 이 잡음은 원래 생성 경로에서는 잘못된 값 반환, Retail에서는 응답 누락을 뜻한다. 이것이 미개선의 원인이라고 단정하지 않는다. 응답 다양성과 학습 표적을 검토할 근거로 남기며 평가 자료를 수정하지 않는다.

최종·후보별 Dev 출력, 후보의 작은 head 가중치·optimizer, 로그·설정·버전은 [원시 결과](evidence/artifacts/action-precision-results.tar.xz)에 있다. 모든 파일의 hash를 결과 JSON에 보존했다. 전체 checkpoint·확장 Train 자료의 공개 배포와 수요 예측 품질, 기존 생성 Test 목표 미달은 남아 있다.
