# 성능 목표와 진행 기록

2026-10-09 주 목표를 [Newsvendor 모수 구성과 정보 요청](research-scope.md)으로 다시 명시했다. 주 평가는 모수·근거, 수요분포, 필요한/불필요한 매니저 호출, 응답 후 회복, 최종 발주 손실이다. 아래 ABCD 90% 목표와 미달 기록은 보조 실험으로 보존하며 주 연구의 완료 기준을 대신하지 않는다. 생성 손실 240.35 미만은 기존 Test와 손실 정의에 대한 비교 기준으로 유지한다.

최신 core 고정 Test의 생성 총손실은 **243.6274**로 기준에 미달했다. 같은 구성기의 no_value·고정 질문은 263.2379였다. Retail Test의 모수·근거 100%, 불필요한 요청·잘못된 발주 진행 0건은 확인했으나 수요분포 품질은 미해결이다. 연구 전체가 완료됐다고 판정하지 않는다. [고정 평가 결과](evidence/research-core-test-results.json)

그 후 Train 출처 안에서 수요 모수 학습 횟수를 선택한 GRU가 세 seed의 사전 Dev 기준을 통과했다. 문서·행동 가중치를 그대로 둔 실제 retail Dev 총손실은 **44.3274 → 24.3925**, 모수·근거 100%, 불필요한 질문·잘못된 진행 0건이었다. 고정 질문·no_value도 같은 손실이었다. 정확한 손실은 고유 기간 5개에 한정하고 Test로 선택하지 않았다. [최신 수요 교체와 제한](demand-selection.md)

새 모델을 고정한 후 별도 출처 27개를 검증했다. 같은 새 자료에서 이전/새 GRU 총손실은 83.1514/69.0309였지만 차이의 95% 구간은 [−31.60, +3.54]로 확실한 개선을 입증하지 못했다. 완전 관측 30개 기간·출처 16개의 결과다. 모수·근거 100%, 필요한 질문·회복 945건과 불필요한 질문·잘못된 진행 0건은 유지됐고 세 정책의 손실은 같았다. 위 기존 Test의 미달 기록과 전체 calibration·전체 모델 공개 과제는 남아 있다. [새 출처 평가와 공개 artifact 재현](retail-holdout.md)

아래는 당시 실행 상태를 포함한 기존 도구 실험의 이력이다. 현재 실행 중인 작업을 의미하지 않는다.

v16은 Dev 개선 없이 종료되었고 초기 가중치를 선택했다. 최종 Dev 도구·인자는 각각 22/32, 호출 precision은 22/26이었다. v16 Test는 수행하지 않았다. 20,480건 checkpoint의 CPU 이력 모듈 제거 비교도 완료되었으며, 켠 조건 20/32 대 끈 조건 21/32로 개선 근거가 되지 않았다. 원시 기록은 `results/l40s-tools-v16`에 유지한다. 주 연구의 base v4 Dev 실행은 완료됐고, 최종 채택 모수·근거 정확도 100%, 불필요한 질문·잘못된 발주 진행 각 0건이다. 정확한 총손실은 5개 관측 기간에 한정되며 학습·고정 질문 정책 모두 44.3274였다. 원시 신경망 모수 정확도는 99.628%이고, 수요분포 및 paired 비교 검증은 아직 남아 있다. [주 연구 기록](research-scope.md)의 분모와 제한을 함께 읽는다.

## 2026-10-08의 도구 실험 목표

사용자가 2026-10-08에 확정한 당시 완료 기준이다. 다음 네 조건을 **동시에** 충족하도록 설정했다.

| 지표 | 완료 기준 | 현재 완료된 v12 |
| --- | ---: | ---: |
| 정답 호출의 도구 완전 일치 | 90% 이상 | 20/26 = 76.9% |
| 도구와 관측 가능한 전체 인자의 완전 일치 | 90% 이상 | 18/23 = 78.3% |
| 호출 precision | 90% 이상 | 20/28 = 71.4% |
| 생성 Test 평균 총손실 | 240.35 미만 | 248.0525 |

이 보조 실험의 위 수치는 미달 기록으로 보존한다. 지표 사이의 교환으로 완료 판정을 대신하지 않는다. 공개 Test는 보호된 96개 ABCD prefix를 대화별 자기 예측 상태로 연결한다. 도구 일치의 분모는 정답 호출 26건, 인자 일치의 분모는 정답 인자가 관측 가능한 호출 23건이다. Precision은 전체 예측 호출을 분모로 한다. 생성 손실은 기존 120개 Test 시나리오의 응답 오류 0 조건에서 실제 출력 발주량의 terminal loss와 요청 비용을 합한 평균이며, 기존 invalid-handoff penalty 정의를 유지한다.

Test는 이미 이전 오류 분석에 사용됐으므로 새 blind Test가 아니다. 이후 모델·설정은 Train·Dev로만 선택한다. 언어·가치 학습과 Dev 선택을 모두 마치고 최종 가중치를 고정한 뒤 Test를 평가한다. 생성 사례 결과를 실제 조직 업무의 효과성 근거로 표현하지 않는다.

v12의 학습·Test 평가를 완료했으나 네 목표를 모두 충족하지 못했다. 선택된 언어 가중치의 Dev는 도구·인자 68.8%, 호출 precision 84.6%, 가치 학습 후 생성 Dev 총손실은 140.1290이었다. 위 표는 고정 **Test** 결과이며 **Dev**와 분모가 다르다. 현재 L40S에서는 선택 가중치로 시작한 v13 후속 학습을 진행한다. 학습률을 낮추고 최신 Train 응답 이후 상태 130개를 추가했으며, 새 단계의 학습 건수를 별도로 계산한다.

## v5 변경

- Dev의 조건부 도구 top-1은 25/32, top-3는 30/32였다. 호출 임계값 변경만으로는 90% 목표에 도달하지 못한다. 후보와 관측 대화가 같은 ModernBERT 입력에서 함께 인코딩되는 경로를 추가했다. 기존 token pointer와 원문 위치는 보존한다.
- 호출 여부와 호출할 도구를 별도로 학습한다. 모든 후보는 공개 도구 스키마에서 만들고, 절차 내용은 관측 대화와 이전 자기 예측 procedure ID로 조회한다. 정답 도구·정답 절차를 추론 후보 생성에 넣지 않는다.
- 기존 구성·상태·인자 head와 encoder를 함께 미세조정한다. 새 행동 경로의 제거 비교는 같은 가중치에서 실행할 수 있다.
- v4의 실제 Train rollout에서 중복과 초기 상태를 제외한 응답 이후 상태 361개를 구성 학습에 추가했다. 입력과 source family를 검증하고 파일 hash를 학습 identity에 기록한다. Test/Dev 상태는 이 replay에 포함하지 않는다.
- 언어 학습을 도구 75%, 구성 20%, 다른 공개 과제 5%로 섞었다. 원래 Train 사례를 모두 유지하면서 작은 과제의 반복 비율을 늘린다. 한 순회는 124,005건이며 고유 사례는 94,498건이다.
- Dev 선택은 도구·인자·precision 중 가장 낮은 값을 우선 개선한다. 도구 지표가 두 번 연속 기준을 충족하면 언어 단계를 조기 종료할 수 있다. 아니면 충분한 Train 순회와 Dev plateau 검사를 계속한다. 행동 가치는 새 구성으로 수집한 실제 rollout에서 다시 학습한다.

실행 설정은 [l40s-tools-v5.json](../configs/l40s-tools-v5.json), 학습 결과 경로는 `results/l40s-tools-v5/base/42/`다. 전체 테스트와 source-group 검사, 수치 smoke를 실행하며 GPU 실측은 `results/l40s-tools-v5/benchmark-final.json`에 저장한다. v5 효과성은 학습과 검증이 끝나기 전까지 미확인이다.

## 첫 Dev 점검

8,192건 학습 후의 Dev는 도구 5/32, 인자 5/32, 호출 precision 5/15로 목표 미달이다. 정답 호출 32건 중 실제 호출한 것은 10건이며, 불필요한 호출은 5건이다. 원시 결과는 `results/l40s-tools-v5/base/42/language-dev-1-8192.jsonl`에 있다. 이 시점에는 새 controller의 조건부 도구 top-1이 9/32인 반면, 함께 학습 중인 기존 선택 경로는 25/32다. 새 선택 경로가 학습 초기에 병목이므로 다음 예정 Dev 점검에서 수렴 추세를 확인한다. 이 결과로 Test를 실행하지 않았다.

Train·Dev의 동일 관측 대화에 서로 다른 도구/발화 정답이 붙은 충돌은 발견되지 않았다. Train 행동은 도구 호출 27,866건과 발화 65,137건이며, 가장 적은 도구도 208건의 주석을 갖는다. 원시 주석 점검은 `results/l40s-tools-v5/checks-train-labels.json`, 코드·자료·수치 검증 기록은 [검증 기록](evidence/performance-goal-checks.json)에 보존한다.

## v6 보정 학습

첫 Dev에서 새 controller가 기존 선택 점수를 활용하지 않고 선택을 다시 배우는 비효율을 확인했다. v5 실행을 보존하고 `configs/l40s-tools-v6.json`에서 기존 점수에 새 controller의 보정값을 더하도록 바꿨다. 호출 판단에도 기존 행동 확률의 호출/비호출 합을 사용하고 새 head가 이를 보정한다. 추가 encoder 연산이나 새 가중치는 필요하지 않으며, 기존 후보 재평가 켜기/끄기도 이 경로에 반영된다.

v5 optimizer checkpoint를 명시적으로 이어받는다. 가중치·optimizer moments·난수 상태·사례 순서는 유지하며 점수 결합 방식 변경을 provenance에 기록한다. 입력·주석·자료 분할·학습률 등의 추가 변경은 continuation 검사에서 거부한다. 이전 최선 checkpoint도 변경된 방식으로 Dev를 다시 평가한 뒤 선택 기준으로 사용한다. v6 성능은 별도로 검증하며, v5의 실패한 초기 결과를 성공 결과로 대체하지 않는다.

v6는 11,264건 checkpoint에서 재개했다. 8,192건 시점의 이전 선택 가중치를 새 방식으로 재평가한 실제 Dev 결과는 도구·인자 각각 19/32 = 59.4%, 호출 precision 19/22 = 86.4%다. 아직 세 목표를 충족하지 않았으며 Test는 실행하지 않았다. 테스트 74개, source-group 검사와 수치 smoke 30건 및 L40S gradient 검사를 통과했다. [v6 검증 기록](evidence/performance-goal-v6-checks.json)에 소스·설정·부모 checkpoint hash와 원시 측정을 연결했다.

16,384건 Dev에서는 도구·인자 각각 21/32 = 65.6%, 호출 precision 21/26 = 80.8%로 변했다. 호출 누락은 12→8건, 불필요한 호출은 2→2건, 잘못 고른 도구는 1→3건이다. 조건부 도구 top-1은 25/32, top-3는 29/32다. 절차 분류는 80/96이며 오류 13건 중 12건에서 절차 top-1이 맞았다. 주된 미달 원인은 올바른 절차를 찾은 이후의 호출 시점과 도구 선택이다.

공개 절차의 도구 목록을 예측된 과거 호출 수로 인덱싱한 진단은 22/32였다. 관측 대화에는 목록 밖의 추가 호출·생략·다른 순서가 있으므로 이 목록을 정답 순서로 강제하면 오류가 생긴다. 실제 Train 대화에서 다음 행동을 학습하는 경로를 유지한다. 원시 오류·절차 점검은 `results/l40s-tools-v6/dev-diagnosis-16384.json`, `dev-measures-16384.json`, `dev-transition-diagnostic-16384.json`에 있다.

24,576건 Dev는 도구·인자 각각 20/32 = 62.5%, 호출 precision 20/28 = 71.4%로 악화돼 채택하지 않았다. 선택 가중치는 16,384건 결과를 유지한다. Train 93,003건의 절차·과거 호출 수별 최빈 도구를 학습하고 Dev의 자기 예측 절차/단계로 조회한 별도 진단도 top-1 25/32에 그쳤다(`train-transition-diagnostic.json`). 이 진단은 다음 행동을 정하는 데 대화 내용이 필요함을 보여주며, 새로운 최종 모델 성능으로 계산하지 않는다. 저장된 모델의 점수별 순위 비교는 `dev-ranking-progress.json`에 보존했다. 숨은 Dev 절차 주석은 사후 채점에만 사용했고 모델 입력이나 Train 빈도에 넣지 않았다.

32,768건에서도 도구·인자 21/32 = 65.6%, 호출 precision 21/29 = 72.4%로 최선 결과를 넘지 못했다. 이 checkpoint 역시 채택하지 않았고 v6 원시 결과와 optimizer checkpoint를 보존했다.

## v7 문맥 점수 직접 학습

v6의 loss는 기존 점수와 새 문맥 점수를 합친 결과를 학습한다. 기존 경로가 이미 맞히는 Train 사례에서는 새 경로의 학습 신호가 작아질 수 있다. `configs/l40s-tools-v7.json`은 합친 점수의 loss를 유지하면서, 새 문맥 경로만의 호출 여부와 조건부 행동 점수에도 동일한 Train 정답으로 cross entropy를 적용한다. 합친 점수가 이미 정답에 확신하더라도 새 문맥 경로에 gradient가 생기는 경우를 검사한다.

입력·가중치 개수·encoder 실행 횟수는 같다. 같은 shape의 optimizer/RNG 상태를 이어받고 loss 추가를 명시적 config 변경으로 기록한다. 이후 성능 개선 여부는 Dev로 검증하며 이 변경 자체를 효과성의 증거로 계산하지 않는다.

33,792건 checkpoint에서 이어가며, 테스트 77개와 source-group·30건 수치 smoke를 통과했다. L40S의 정상 구간 처리량은 11.46건/초다. [v7 검증 기록](evidence/performance-goal-v7-checks.json)에 원시 측정과 가중치 출처를 보존했다.

40,960건의 첫 v7 Dev는 도구·인자 19/32 = 59.4%, 호출 precision 19/22 = 86.4%로 최선 기준을 넘지 못했다. 조건부 도구 top-1은 기존 경로 27/32, 새 문맥 경로 13/32, 결합 26/32다. 호출 임계값만 조정해 세 지표를 90%로 만들 수 있는 상태는 아니다. Train 호출 빈도를 이용한 점수 보정 진단도 정답 호출 20/24에 그쳤으며 최종 모델에 채택하지 않았다. `dev-diagnosis-40960.json`에 기록한 점수 재조합은 실제 새 대화 replay가 아니므로 모델 성능으로 보고하지 않는다.

새 보조 손실은 Train에서 호출 판단 0.638→0.461, 조건부 행동 1.374→0.842로 감소했다(처음/최근 256건 비교, `auxiliary-training-check.json`). 이 측정은 Dev 개선을 입증하지 않는다. 저장된 자기 예측 memory로 Dev 입력 96건을 재구성한 검사에서는 controller 대화 문맥 잘림이 0건이었다(`dev-controller-coverage.json`). v7 학습을 계속하며 선택 가중치는 이전 16,384건 최선 모델을 보존한다.

49,152건 Dev도 도구·인자 19/32 = 59.4%, 호출 precision 19/22 = 86.4%였다. 문맥 경로의 조건부 top-1은 13→19/32로 개선됐으나, 결합한 최종 결정은 개선되지 않았다. 57,344건에서는 도구·인자 19/32, 호출 precision 19/24 = 79.2%로 여전히 미달했다. v7은 원시 결과와 58,368건 optimizer checkpoint를 보존하고 다음 입력 결함 수정으로 이어간다.

## v8 공개 정책의 실행 조건 보존

정책 요약이 행동 이름만 남겨 공개 행동 설명 255개와 세부 설명이 있는 209개 항목의 조건을 전달하지 않는 결함을 확인했다. 원문 정책 자체는 별도의 chunk 검색 경로에 남아 있었지만, controller와 절차 요약에는 해당 문구가 없었다. `Website Too Slow` 등의 `Option 1`, `Option 2`는 대안인데도 요약은 이를 `Steps`로 표시했다. 또한 과거 호출 횟수를 목록 인덱스로 사용하는 재평가 특성은 생략·분기·반복을 실제 업무 단계로 오인할 수 있다.

`configs/l40s-tools-v8.json`은 선택한 공개 절차의 행동 설명과 세부 조건, 발화 지시를 원문 표현대로 controller에 넣는다. 후보를 정답 절차로 제한하지 않으며 모든 허용 도구를 계속 비교한다. 요약은 `Actions`로 표시하고, 호출 횟수를 목록 위치로 변환하던 특성은 사용하지 않는다. 진행 출력의 `stageMeaning`은 현재 보조 head가 학습하는 값이 상한 15의 과거 호출 수임을 명시한다. 이를 실제 workflow node 정확도로 보고하지 않는다.

공개 절차 세 개의 최대 길이 상한을 측정해 정책 1,536 tokens, 전체 controller 3,072 tokens로 정했다. 선택한 정책 조건이 예산을 넘으면 조용히 자르지 않고 검사를 실패시킨다. Train 256건과 Dev 96건의 관측 입력 검사에서는 최대 controller 길이 2,100 tokens, 대화 잘림 0건이었다. 이 검사는 입력 커버리지 검사이며 성능 검증은 아니다(`results/l40s-tools-v8/policy-context-audit.json`).

기존 가중치·optimizer moments·난수·사례 순서를 이어가되 세 입력 설정의 명시적 변경을 continuation 기록에 남긴다. 부모의 최선 가중치는 새 입력으로 Dev에서 다시 평가한다. 기존 실행은 저장된 설정에서 종전 입력 구성을 재현할 수 있다. 단위·회귀 테스트 80개와 lint를 통과했다. 이후 학습 및 실제 rollout 성능은 별도로 검증한다.

L40S 정상 구간의 전체 역전파 실측은 8.36건/초, 최대 GPU 메모리는 41,126,066,176 bytes였다. source-group 겹침 0건, 보호된 snapshot 불변, 수치 smoke 30건을 확인했다. 실제 가져온 checkpoint의 가중치와 232개 optimizer 상태가 부모와 같은지도 비교했다. [v8 검증 기록](evidence/performance-goal-v8-checks.json)에 원시 측정과 실행 hash를 연결했다.

새 입력으로 부모의 선택 가중치를 재평가한 Dev 기준값은 도구·인자 20/32 = 62.5%, 호출 precision 20/25 = 80.0%다. 이는 수정된 입력에서 추가 학습하기 전 측정이며, v8의 학습 효과로 해석하지 않는다. 목표는 아직 미달이다.

## v9 패딩 연산 최적화

v8는 정상적으로 학습했으나 전체 처리량이 약 7건/초였다. 긴 controller와 짧은 문서·query를 같은 encoder 묶음에 넣는 패딩 비용을 측정했다. Train 256건의 입력 토큰 수를 유지하면서 묶음 내 패딩 비율을 1.25 이하로 제한하면 예상 패딩 토큰이 1,398,528→1,207,680으로 13.6% 줄었다. 이 추정만으로 적용하지 않고, 같은 초기 가중치와 Train 64건에서 전체 역전파를 비교했다.

| 설정 | 정상 구간 처리량 | 최대 GPU 메모리 |
| --- | ---: | ---: |
| 기존 묶음, token limit 65,000 | 8.20건/초 | 41.13GB |
| padding ratio 1.25, token limit 65,000 | 10.57건/초 | 42.37GB |
| padding ratio 1.25, token limit 70,000 | 10.99건/초 | 42.37GB |

70,000 설정은 해당 입력에서 분할·실제 인코딩 토큰·손실이 65,000 설정과 같았다. 따라서 padding ratio 1.25만 채택하고 기존 token limit을 유지한다. 약 29%의 개선은 이 처리량 probe의 측정이며 전체 학습 시간 개선율이나 정확도 향상을 의미하지 않는다. 원문 입력·라벨·head·학습률·gradient accumulation은 바꾸지 않았다. 전체 인코딩 토큰 수의 감소는 더 큰 묶음에서 공유 schema query 중복을 줄인 결과이며 입력을 잘라낸 결과가 아니다.

원시 결과는 `results/l40s-tools-v8/padding-benchmark.json`, 실행 소스는 같은 폴더의 `padding-benchmark-source.tar.gz`에 보존한다. 출력·pointer·encoder gradient 보존을 포함한 테스트 82개, lint, source-group 검사와 수치 smoke 30건을 통과했다. `configs/l40s-tools-v9.json`으로 v8의 62,464건 optimizer checkpoint를 이어간다. 모델의 성능 완료 기준은 바꾸지 않는다.

실제 Dev 대화 replay 96건에서도 동일한 부모 가중치의 행동·도구·인자·절차 선택이 모두 유지됐다(`results/l40s-tools-v9/runtime-retention.json`). [v9 검증 기록](evidence/performance-goal-v9-checks.json)은 실행 source hash와 실제 가져온 가중치·232개 optimizer 상태의 일치 검사를 보존한다.

65,536건 Dev는 도구·인자 18/32 = 56.3%, 호출 precision 18/22 = 81.8%로 부모 선택 가중치를 넘지 못해 채택하지 않았다. 실제 오류는 필요한 호출 누락 12건, 잘못 고른 도구 2건, 불필요한 호출 2건이다. 조건부 도구 top-1은 기존 경로 26/32, 문맥 경로 19/32, 결합 25/32였다. 정답 도구의 내부 인자 목록은 30/32에서 일치했지만, 이 중에는 실제로 선택하지 않은 도구와 인자가 없는 호출이 포함되므로 이를 인자 목표 달성으로 계산하지 않는다. 원시 진단은 `results/l40s-tools-v9/dev-diagnosis-65536.json`에 있다.

정책 조건을 보존한 입력으로 학습한 분량은 이 시점에 7,168건이다. 입력과 목표를 다시 바꾸지 않고 예정된 Train 순회와 Dev 점검을 계속한다. 실제 학습 처리량은 약 8.9건/초로 측정됐다. Test와 생성 총손실은 이 변경의 완료 성능으로 아직 재평가하지 않았다.

73,728건 Dev는 도구·인자 20/32 = 62.5%, 호출 precision 20/27 = 74.1%로 채택하지 않았다. 호출 누락은 12→9건으로 줄었지만 잘못된 도구는 2→3건, 불필요한 호출은 2→4건으로 늘었다. 문맥 경로의 조건부 top-1은 19→22/32, 결합은 25→24/32였다(`dev-diagnosis-73728.json`). 입력 수정 뒤 직접 학습한 고유 도구 사례는 70,656건 checkpoint 기준 9,216/93,003건이었다. 이 노출 수에는 별도의 조회·다음 턴 보조 학습을 포함하지 않는다(`input-exposure.json`).

## v10 후보 재평가 학습 연결 수정

재평가를 끈 설정에서 `recovery`와 `baseRecovery`가 모두 기본 점수였기 때문에, 두 손실이 같은 기본 점수를 학습하고 `rerankDelta`에는 gradient를 주지 않는 결함을 확인했다. 74,752건 checkpoint의 재평가 파라미터 네 개는 v3의 값과 완전히 같았다(`results/l40s-tools-v9/reranker-training-audit.json`). 따라서 그 상태의 재평가 전후 차이는 현재 입력에 맞춰 재학습한 모듈의 효과로 해석할 수 없다.

`rerankSupervision` 설정은 두 recovery 손실을 기본 점수와 재평가 점수에 각각 연결한다. 손실 항 수와 encoder 실행 횟수, 파라미터 수는 늘리지 않는다. 추론에서 재평가를 꺼도 해당 head의 학습은 유지된다. 이 경우에도 gradient가 발생하고, 추론 토글이 학습 objective를 바꾸지 않는 회귀 테스트를 추가했다.

`configs/l40s-tools-v10.json`은 수정된 재평가 경로를 켠 구성으로 학습하며 동일 가중치의 끄기/켜기 비교를 유지한다. v9의 77,824건 optimizer checkpoint를 이어가고, 점수 경로 변경은 continuation에 명시한다. 기존 encoder·상태·인자·문맥 head와 optimizer 상태를 보존한다. 재평가 가중치의 실제 갱신은 GPU 검사에서 별도로 확인한다. 성능 목표 충족 여부는 이후 Dev 및 최종 평가로 검증한다.

테스트 84개, lint, source-group 검사와 수치 smoke 30건을 통과했다. L40S 역전파 probe는 정상 구간 10.02건/초, 최대 42.37GB이며 재평가 head의 gradient와 파라미터 갱신을 확인했다. 실제 78,848건 학습 checkpoint에서도 재평가 파라미터 네 개가 모두 변경됐고 optimizer 상태는 232→236개로 늘었다. [v10 검증 기록](evidence/performance-goal-v10-checks.json)에 근거를 보존한다.

재평가 경로를 켜서 재검증한 부모 선택 가중치의 Dev는 도구·인자 20/32 = 62.5%, 호출 precision 20/25 = 80.0%다. 학습 연결 수정 전의 기준값으로 기록하며, 이후 목표 성능 달성 여부는 미확인이다.

81,920건의 첫 v10 Dev는 도구·인자 19/32 = 59.4%, 호출 precision 19/26 = 73.1%로 채택하지 않았다. 필요한 호출 누락 10건, 잘못 고른 도구 3건, 불필요한 호출 4건이다. 조건부 top-1은 기본 및 재평가 점수 각각 25/32, 문맥 점수 22/32, 최종 결합 26/32였다. 이 시점의 재평가 제거 점수 재조합도 26/32로 같았으며, 이는 저장된 상태에서의 순위 진단이다. 다른 선택으로 대화 상태까지 다시 진행한 ablation 성능을 뜻하지 않는다(`results/l40s-tools-v10/dev-diagnosis-81920.json`).

90,112건 Dev도 도구 18/32 = 56.3%, 인자 17/32 = 53.1%, 호출 precision 18/24 = 75.0%로 채택하지 않았다. v10은 95,232건 optimizer checkpoint와 원시 결과를 보존하고 아래 단계 표적 수정으로 이어간다. 고정 Test는 실행하지 않았다.

## v11 실제 Train 흐름에 따른 진행 상태 학습

기존 진행 head의 정답은 과거 호출 횟수였다. 따라서 이를 잘 맞혀도 실제 절차의 다음 행동을 배웠다고 볼 수 없었다. `workflowProgress`는 이 표적을 현재 절차 안에서 다음으로 기록된 도구의 공개 목록 위치로 바꾼다. 실제 대화에서 생략·다른 순서·반복 호출을 허용하며, 목록의 앞 항목부터 실행해야 한다고 가정하지 않는다. 여러 위치에 같은 도구가 있으면 가능 위치들의 likelihood를 합산한다.

단계 분포는 절차별로 예측한다. 기존 16차원 head를 관측 문맥과 해당 절차 표현에 적용하고, 자기 예측 절차 확률과 단계 확률로 도구 재평가 특성을 만든다. 현재 호출 횟수를 목록 인덱스로 사용하는 방식은 새 설정에서 제거된다. 공개 목록 밖의 도구도 행동 후보에 남는다. 출력의 `nextNodes`는 예측한 도구 위치와 원문 정책의 document/span을 보존한다. 마지막 범주는 ‘기록에 이후 도구 호출 없음’이며 업무 성공이나 완료를 인증하지 않는다.

미래 도구 주석은 허용된 현재 Train ID이면서 원천의 공식 Train인 경우에만 **loss 표적**으로 읽는다. 모델 입력·검색 후보·추론 상태에는 넣지 않는다. 93,003건 중 60,145건은 공개 도구 위치, 25,287건은 이후 기록된 호출 없음으로 연결된다. 공개 목록에 매핑되지 않는 7,514건과 공식 Train 밖에서 유래한 기존 Train 57건은 단계 손실을 적용하지 않는다. 기존 Train/Dev/Test 분할은 바꾸지 않았다. `results/l40s-tools-v11/workflow-target-audit.json`에 표적 hash와 자료 hash, 누출 검사를 보존한다.

가중치 shape와 encoder 입력은 유지한다. 목표 의미 변경을 continuation에 명시하고 부모 optimizer·난수 상태·사례 순서를 보존하며 부모 선택 가중치를 새 방식으로 재검증한다. 실행 설정은 `configs/l40s-tools-v11.json`, 부모는 v10의 95,232건 checkpoint다. 테스트 89개와 lint, 출처 그룹 겹침 0건, 30개 서로 다른 family의 수치 smoke를 통과했다. 수정의 성능 효과와 목표 달성 여부는 아직 미확인이다.

L40S 전체 역전파 probe의 정상 구간은 9.88건/초, 최대 42,372,127,232 bytes다. Train 64건 중 39건에 새 단계 표적이 적용되며, 진행 head와 재평가 head의 gradient 및 가중치 갱신을 확인했다. 추가 encoder 통과는 없다. 원시 측정과 source hash는 [v11 검증 기록](evidence/performance-goal-v11-checks.json)과 `results/l40s-tools-v11/benchmark.json`에 보존한다.

실제 가져온 가중치·236개 optimizer 상태·난수·사례 순서의 일치를 확인했다(`continuation-check.json`). 부모 선택 가중치를 재평가한 Dev는 도구·인자 20/32 = 62.5%, 호출 precision 20/25 = 80.0%로 유지됐다. 이는 새 표적으로 추가 학습하기 전 기준값이다. 실제 96,256건 checkpoint에서도 진행·재평가 head의 모든 파라미터가 갱신됐다(`workflow-training-check.json`). 새 단계 손실의 첫 128개 평균은 3.814, 최근 128개는 1.223이다(`workflow-loss-check.json`). 이 Train 측정은 Dev 정확도 개선의 증거로 계산하지 않는다.

98,304건의 첫 v11 Dev는 도구 20/32 = 62.5%, 인자 18/32 = 56.3%, 호출 precision 20/25 = 80.0%다. 인자 성능이 부모 선택 가중치보다 낮아 채택하지 않았다. 필요한 호출 누락 11건, 잘못된 도구 1건, 불필요한 호출 4건이 남았다. 선택한 절차의 다음 노드가 현재 정답 도구와 일치하는 것은 호출 사례 23/32이지만 이는 실제 실행 정확도가 아니다. 원시 진단은 `results/l40s-tools-v11/dev-diagnosis-98304.json`에 있다. 새 표적을 적용한 추가 학습은 3,072건이며 예정된 Train 순회와 Dev 선택을 계속한다. 생성 총손실 및 고정 Test는 아직 재평가하지 않았다.

106,496건 Dev는 도구·인자 18/32 = 56.3%, 호출 precision 18/22 = 81.8%로 채택하지 않았다. 호출 누락 12건, 다른 도구 선택 2건, 불필요한 호출 2건이다. 저장된 상태에서의 조건부 도구 top-1은 25/32이므로 호출 임계값만 조정해 도구 일치 90%를 달성할 수 있는 상태가 아니다. 절차의 다음 도구 위치는 25/32에서 현재 정답 도구와 같았다. `dev-diagnosis-106496.json`에 진단을 보존하고, v11은 107,520건 checkpoint에서 아래 역할 주석 수정으로 이어간다.

## v12 원천 슬롯의 역할 주석 연결

첫 v11 Dev의 인자 오류 두 건은 이름 span의 끝 위치와 사유 선택 오류였다. 조립기가 맞는 인자를 거절한 사례는 없었다. 이어서 공식 Train의 원천 `scenario`에 있는 이름·계정번호·주문번호 등의 슬롯을 실제 호출 인자와 대조했다. 인자 28,579개 중 기존 역할 손실은 8,821개에만 적용되고, 원천 슬롯과 일치하면서 해당 도구에 선언된 역할 16,587개를 추가로 학습할 수 있음을 확인했다. 감사 기록은 `results/l40s-tools-v11/role-supervision-audit.json`이다.

`training.sourceRoleSupervision`은 이 슬롯 값을 모델 입력에 넣지 않고 Train loss의 역할 이름 표적으로만 사용한다. 기존 enum처럼 하나의 값이 여러 역할을 나타낼 때는 기존 marginal label을 유지한다. 목록에 없는 역할을 새로 만들어 붙이지 않는다. 공식 Train 밖의 사례에는 새 역할 주석을 붙이지 않으며 기존 자료 분할을 유지한다. 기존 가중치·optimizer shape·추론 입력은 그대로다.

테스트 92개, lint와 전체 Train 표적·출처 그룹 검사, 30개 family의 수치 smoke를 통과했다. 변경 소스와 설정은 `results/l40s-tools-v12/staged-source.tar.gz`, 검증 hash는 `staged-checks.json`에 보존했다. L40S의 Train 64건 probe에서 기존에 없던 역할 표적 10개가 추가됐고 역할·진행·재평가 head의 gradient와 가중치 갱신을 확인했다. 정상 구간 처리량은 9.72건/초, 최대 메모리는 42,371,512,832 bytes다.

`configs/l40s-tools-v12.json`으로 v11의 107,520건 checkpoint를 이어간다. 저장된 가중치·236개 optimizer 상태·난수·사례 순서의 일치를 확인했고, 역할 loss 표적 추가를 continuation에 명시했다. 실행 근거는 [v12 검증 기록](evidence/performance-goal-v12-checks.json)에 보존한다. 성능 개선 및 네 가지 완료 기준 충족은 아직 검증되지 않았다.

실제 108,544건 checkpoint에서도 역할 head 가중치 갱신을 확인했다. 추가 구간의 역할 손실 측정은 191건, 평균 0.671이며 학습에 사용한 표적 hash는 사전 감사와 일치한다(`role-training-check.json`). 부모 선택 가중치 재평가는 도구·인자 62.5%, 호출 precision 80.0%로 동일했다. 이 값은 v12의 추가 학습 성과가 아니며 첫 예정 Dev는 114,688건이다.

114,688건의 첫 v12 Dev는 도구·인자 22/32 = 68.8%, 호출 precision 22/26 = 84.6%로 기존 최선 기준을 넘어 채택됐다. 필요한 호출 누락은 8건, 잘못 고른 도구는 2건, 불필요한 호출은 2건이다. 조건부 도구 top-1은 25/32, top-2는 30/32다. `dev-diagnosis-114688.json`에 원시 진단을 보존한다. 추가 언어 학습이 함께 진행됐으므로 이 변화 전체를 역할 주석 추가만의 독립적 효과로 계산하지 않는다. 예정된 학습과 Dev 선택을 계속한다.

122,880건 Dev는 도구·인자 18/32 = 56.3%, 호출 precision 18/22 = 81.8%로 악화돼 채택하지 않았다. 호출 누락 12건, 잘못 고른 도구 2건, 불필요한 호출 2건이다. 최선 가중치는 114,688건 결과를 유지한다. 다음 도구 위치는 26/32에서 맞았지만 실제 선택한 도구가 맞은 수는 18건이므로, 단계 예측을 실행 성능으로 대신 보고하지 않는다. 원시 진단은 `dev-diagnosis-122880.json`에 보존했다.

124,005건의 첫 순회 종료 Dev는 도구 23/32 = 71.9%, 인자 21/32 = 65.6%, 호출 precision 23/32 = 71.9%다. 필요한 호출 누락 6건, 잘못 고른 도구 3건, 불필요한 호출 6건으로, 더 많이 호출하면서 precision이 낮아졌다. 기존에 선언한 세 지표의 최솟값 우선 선택 기준을 넘지 못해 채택하지 않았다. 최선은 여전히 114,688건 가중치이며, 같은 설정으로 두 번째 순회를 진행한다. 원시 진단은 `dev-diagnosis-124005.json`에 보존했다.

누적 132,197건(두 번째 순회 8,192건) Dev는 도구 18/32 = 56.3%, 인자 17/32 = 53.1%, 호출 precision 18/23 = 78.3%로 채택하지 않았다. 필요한 호출 누락 13건, 잘못 고른 도구 1건, 불필요한 호출 4건이다. 정답 도구를 선택한 뒤 이름 span에 계정번호가 붙는 인자 오류도 1건 있었다. 조건부 도구 top-1은 25/32, top-3는 31/32이며 이것을 실제 실행 정확도로 계산하지 않는다. 최선 가중치는 114,688건을 유지하고 연속 미개선은 3회다. 원시 파일 hash를 포함한 `dev-diagnosis-132197.json`에 진단을 보존했다.

실제 shuffle 순서로 학습 노출량을 따로 확인했다. 누적 132,197건 중 역할 표적 수정 뒤의 일차 학습은 24,677건이고, 그 안의 고유 도구 사례는 17,754/93,003건(19.1%)이다. 원천 역할 주석이 있는 사례는 2,393/12,338건을 보았다. 실제 진행 상태 표적을 연결한 뒤의 고유 도구 사례는 26,343건(28.3%), 재평가 gradient를 연결한 뒤에는 38,629건(41.5%)이다. 추가 조회·다음 턴 보조 학습은 이 수에 포함하지 않는다. 부모 실행의 학습량을 포함한 `minCases`를 새 표적으로 전체 Train을 순회했다는 근거로 사용하지 않는다. 현재 실행의 설정과 선택 규칙은 유지하며, 이 노출량과 별도의 성능 결과를 함께 남긴다(`supervision-exposure-132197.json`).

저장된 Dev 예측을 원천 절차 주석으로 사후 채점했다. 선택된 114,688건 모델의 절차 top-1은 81/96, top-3는 96/96이다. 정답 호출에서는 각각 27/32, 32/32이며, 실제 도구 오류 10건 중 9건은 절차 top-1을 맞힌 상태였다. 4건은 예측한 다음 도구까지 맞았지만 실제로 호출하지 않았다. 132,197건 모델도 도구 오류 14건 중 11건에서 절차를, 9건에서 다음 도구를 맞혔으나 호출을 누락했다. 따라서 절차 검색 누락만으로 전체 오류를 설명할 수 없다. 다음 도구 표적은 미래의 기록된 호출을 포함하므로 이 일치 자체를 즉시 호출해야 한다는 준비 상태나 실행 성공으로 계산하지 않는다. 주석은 저장된 Dev 출력의 사후 채점에만 사용했으며 원문 및 예측 hash와 개별 기록은 `procedure-diagnosis.json`에 보존했다.

140,389건 Dev는 도구·인자 19/32 = 59.4%, 호출 precision 19/24 = 79.2%로 채택하지 않았다. 호출 누락 11건, 잘못 고른 도구 2건, 불필요한 호출 3건이다. 절차 top-1은 전체 89/96이며 정답 호출에서는 32/32였지만, 다음 도구 일치는 27/32, 실제 도구 일치는 19/32였다. 실제 도구 오류 13건 모두 절차는 맞았고, 그중 7건은 다음 도구도 맞았으나 호출하지 않았다. 연속 미개선은 4회다(`dev-diagnosis-140389.json`).

저장된 점수에서 재평가 delta의 역할도 확인했다. 114,688·132,197·140,389건 모두 정답 호출 32건의 조건부 도구 top-1은 delta를 더하거나 빼도 바뀌지 않았다. 140,389건에서 delta 절댓값 평균은 0.819, 최대는 4.188이고, 최종 조건부 top-1과 top-2 점수 차이의 중앙값은 8.143이다. 이는 학습된 delta가 존재해도 이 사례들의 도구 순위를 수정하지 못했다는 관측이다. 호출 gate와 이후 자기 상태까지 다시 진행한 결과는 아니므로 재평가 모듈 전체의 성능 효과가 없다는 ablation 결론으로 사용하지 않는다. 개별 점수와 원시 hash는 `rerank-score-diagnosis.json`에 보존했다.

148,581건에서 도구 20/32 = 62.5%, 인자 19/32 = 59.4%, 호출 precision 20/28 = 71.4%를 기록해 연속 미개선 5회로 언어 학습을 종료했다. 마지막 가중치는 채택하지 않았다. `language-done.pt`와 `common.pt`의 모든 가중치 hash가 114,688건 선택 모델의 hash와 정확히 같은 것을 확인했다(`language-selection-restored.json`). 이 선택 모델의 가치 학습 전 생성 Dev 60건 평균 총손실은 399.3742다. 이어서 Train 360개 생성 시나리오의 실제 자기 상태 rollout으로 가치 head를 학습한다. 이 Dev 값은 최종 Test의 총손실이 아니다.

가치 학습은 752개와 613개의 자기 상태를 두 차례 수집해 완료했다. 첫 수집의 10 epoch에서 생성 Dev 총손실 140.1290을 기록한 후보를 선택했고, 이후 후보들은 이를 넘지 못했다. `common.pt` 대비 실제로 바뀐 파라미터는 가치 head의 weight/bias 네 개뿐이며 나머지 구성 가중치의 완전 일치, 최종 `model.pt`와 선택된 `policy-done.pt`의 완전 일치를 확인했다(`policy-retention-check.json`). 공개 Dev는 도구·인자 22/32, 호출 precision 22/26으로 유지됐다. 학습 프로세스가 종료된 뒤 가중치·설정·자료·소스 hash를 `final-evaluation-freeze.json`에 고정하고 Test 비교를 시작했다. 최종 목표 달성 여부는 해당 Test 결과로 별도 판단한다.

### 최종 평가의 범위 정정

원래 완료 기준은 고정 Test의 네 지표다. 실행기에는 Dev에서도 동일한 네 기준을 통과해야 Test 비교로 넘어가는 추가 제한이 있었다. 이 제한은 사용자가 확정한 완료 기준에 포함되지 않았으므로, 현재 실행의 언어·가치 학습과 Train/Dev 선택이 **모두 끝난 뒤** 최종 가중치를 동결해 고정 Test를 평가한다. 실행 중인 학습 소스와 선택 규칙은 바꾸지 않는다. 실행기가 `dev_goal_not_met`로 끝나더라도 저장된 최종 checkpoint를 정해진 비교 함수로 평가한다.

실행 전 계획과 조건은 `results/l40s-tools-v12/final-evaluation-plan.json`에 기록했다. 완료된 체크포인트와 파라미터 hash를 먼저 고정하며, Test 결과로 재평가 토글·체크포인트를 다시 고르지 않는다. 최종 네 조건을 모두 충족해야 완료로 판정한다.

`scripts/finalize_tools.py --run results/l40s-tools-v12/base/42 --wait`가 실제 학습 PID의 종료를 기다린다. 학습 중이거나 실패·중단된 실행, 누락된 산출물, 바뀐 소스·설정·자료·가중치는 평가 전에 거부한다. 중복 실행은 프로세스 잠금으로 막고, 완료된 동일 비교는 재사용한다. 중단된 평가를 재시도할 때는 기존 원시 측정을 별도 archive에 보존한다. 설정된 재평가 토글의 결과로 목표를 다시 계산하며, 캐시된 성공 표시나 더 유리한 Test 토글을 선택하지 않는다. 마지막 기록 보존 추가까지 포함한 전체 테스트 96개(16.37초)와 lint를 통과했다. 학습 소스 hash는 바뀌지 않았다.

## 관측 대화 순서의 상태 모듈 검증안

`/tmp/newsvendor-dialogue-state`에 현재 실행과 분리된 수정안을 만들었다. 기존 controller 토큰에서 각 관측 발화의 위치를 보존해 표현을 모으고, 화자 표현과 자기 예측 과거 도구 표현을 GRU(hidden 128)에 시간순으로 넣는다. 결과는 호출·도구 선택 head의 상태에 더한다. 초기 projection은 0으로 설정해 기존 부모의 판단에서 출발한다. encoder 입력·원문 위치·추가 encoder 통과 없이 293,712개 파라미터를 더하며 전체는 152,473,626개다. 과거 도구 추론 결과에는 history 위치와 예측 확률을 기록한다.

공식 Train의 과거 도구 주석 188,138개는 auxiliary loss에만 사용한다. 실제 관측 prefix와 원천 이력의 일치를 확인한 70,446건에 적용하며, 현재/미래 주석과 공식 비Train 자료에는 이 손실을 붙이지 않는다. 준비된 입력이나 순차 상태에 정답 도구를 복사하지 않는다. 대화가 잘리면 각 발화의 부분 관측 여부를 보존한다. 동일 가중치로 이 상태 모듈을 끈 추론 비교도 추가했다.

전체 테스트 102개, lint, 출처 그룹 검사와 30개 family 수치 smoke를 통과했다. 실제 고정 revision의 encoder와 부모 checkpoint를 CPU에서 불러와 기존 가중치 완전 일치, encoder 입력·원문 위치 일치, 초기 호출·도구·span·모드·가치 출력 차이 0을 확인했다. 자기 예측 후속 상태의 forward/backward에서 encoder·과거 도구 인식·GRU·projection까지 gradient를 검사했다. 수정안 source hash는 `704c6949699a1884fda61bfcb1a7fdfacdca25c88c52ec9acd23c08b1699b165`이며 patch·archive·검증 원시는 `results/dialogue-state-prototype/checks.json`에 있다.

L40S에서 같은 부모·Train 64건·seed로 상태 모듈 끄기/켜기를 비교했다. 두 번째 반복은 각각 6.6384초(9.6409건/초), 6.6452초(9.6311건/초)였고 최대 할당은 42,518,724,608·42,522,445,824 bytes다. 자기 예측 후속 상태 차이로 인코딩 토큰은 각각 242,859·242,559개였다. 한 번의 정상 반복으로 속도 향상을 주장하지 않는다. 초기 0 projection의 첫 update에서는 GRU gradient가 0이고 다음 update부터 전달됨을 포함해 인식 head·GRU·projection의 실제 gradient와 갱신을 확인했다. ## 순차 상태와 절차·진행 학습의 연결 검증안

v15의 순차 상태는 controller에서 계산되지만, 절차/진행 head는 그 전에 실행된다. 실제 production head를 사용한 작은 CPU graph에서 projection을 0이 아닌 값으로 설정한 뒤 검사했을 때, 절차·진행 손실의 History 모듈 gradient는 0이고 controller 손실의 gradient는 양수였다. encoder는 두 손실에 공유되므로 전체 학습 경로가 독립이라는 뜻은 아니다(`results/l40s-tools-v15/history-workflow-gradient-audit.json`).

`/tmp/newsvendor-workflow-state`에 `encoder.dialogueWorkflow` 수정안을 분리했다. 기존 GRU 상태를 한 번 계산해 절차 검색·진행·controller·후보 재평가에 공유한다. 새 파라미터나 encoder 실행은 없다. projection이 0일 때는 기존 입력·원문 위치·head 출력이 같고, projection이 학습된 뒤에는 진행 손실이 GRU 및 인식 모듈과 encoder까지 직접 전달된다. 기존 가중치 shape와 optimizer·난수·case 순서를 보존하는 명시적 continuation도 지원하며 새 graph에서 저장된 best 가중치를 재검증한다.

전체 테스트 105개(19.12초), lint와 30개 family 수치 smoke를 통과했다. 실제 v15 8,192건 checkpoint를 CPU에서 strict load해 모든 가중치 완전 일치와 총 152,473,626개 파라미터를 확인했다. 데이터 identity는 v15와 같고 기존 출처 그룹 감사를 재사용한다. 수정안 source hash는 `0917868a01a2fe4653420882048dfbdbaef944c064bf588e8fcddf6030d05d28`이다. [검증 기록](evidence/workflow-state-checks.json)에 source archive·patch·검증·GPU 비교 설정을 보존했다. 같은 학습된 부모 가중치·Train 64건·seed의 L40S 비교를 완료했다. 두 번째 반복은 연결 전 6.9239초(9.2433건/초), 연결 후 6.9298초(9.2355건/초)였고 두 조건 모두 242,278 tokens를 처리했다. 최대 할당은 각각 42,522,445,824·42,522,461,184 bytes이며 인식·GRU·projection·진행·재평가 head의 gradient와 갱신을 확인했다. 단일 반복으로 속도 향상을 주장하지 않는다. 이전 실행과 진단 프로세스가 모두 종료된 뒤 검증된 파일을 byte 단위로 동일하게 본 코드에 적용했다. 정확도 효과는 아직 미확인이다.


v15는 03:42 UTC에 Dev 목표 미달로 종료했다. 마지막 16,384건은 도구 20/32, 인자 19/32, 호출 precision 20/23이며 채택하지 않았다. 과거 도구 인식은 171/176(97.16%), 가장 최근 과거 도구는 71/74였지만 다음 행동의 성능은 개선되지 않았다. 초기 언어 가중치 완전 복원을 확인했고 가치 학습 뒤 Dev는 도구·인자 22/32, 호출 precision 22/26, 생성 총손실 140.129다. v15의 고정 Test는 실행하지 않았다(`results/l40s-tools-v15/final-development-audit.json`).

## v16 순차 상태를 업무 진행 판단에 연결

03:49 UTC에 `configs/l40s-tools-v16.json`으로 L40S 학습을 시작했다. v15의 미채택 16,384건 중간 checkpoint에서 현재 가중치·optimizer·난수·데이터 순서를 유지하는 명시적 실험 continuation이다. 과거 도구 인식을 새로 초기화하지 않으며 저장된 최선 가중치를 새 계산 경로에서 재검증한다. 최종 조기 종료 checkpoint는 epoch가 넘어갔으므로 사용하지 않고 epoch 0/offset 16,384인 보존 snapshot을 사용한다. 새 실험의 채택 여부는 Train/Dev로 다시 판단한다.

유일한 구조 설정 변경은 `encoder.dialogueWorkflow=true`이며 자료·분할·주석·학습률·최대 학습량·목표는 유지한다. 다음 Dev는 누적 20,480건이다. 저장된 best를 재검증한 뒤 연속 미개선 횟수를 초기화하며 이후 세 번 미개선이면 종료한다. 새 파라미터나 encoder 통과는 없다. source hash는 `0917868a01a2fe4653420882048dfbdbaef944c064bf588e8fcddf6030d05d28`이며 [v16 실행 기록](evidence/performance-goal-v16-checks.json)에 부모 checkpoint·설정·자료·실행 정보를 보존한다. Dev의 네 기준을 모두 통과한 뒤에만 고정 Test를 평가한다. 성능 목표는 아직 달성하지 못했다.


16,384건 부모 snapshot의 현재 가중치·optimizer·난수·case 순서가 v16에 완전히 같은 값으로 복원됐음을 확인했다. 저장된 best를 재검증한 결과는 도구·인자 22/32, 호출 precision 22/26으로 이전과 같다. 첫 추가 1,024건(누적 17,408건)에서는 optimizer 최대 step이 512에서 544로 증가했고 encoder embedding·History의 8개 파라미터·진행 및 재평가 가중치가 모두 갱신됐다. 원시는 `continuation-import-check.json`, `continuation-update-check.json`에 있다.

04:00 UTC, 누적 20,480건의 첫 새 Dev는 도구·인자 20/32(62.5%), 호출 precision 20/24(83.33%), 호출 누락 11건·잘못된 도구 1건·불필요한 호출 3건으로 탈락했다. 잠재 인자 목록은 29/32였고 과거 도구 인식은 172/176(97.73%), 가장 최근 과거 도구는 71/74였다. 초기 선택 모델을 유지하며 다음 예정 검증까지 학습한다. GPU의 원래 평가와 별도로 동일 20,480건 가중치의 상태 연결 켜기/끄기 CPU Dev replay를 실행한다. CPU 결과를 원래 GPU 목표 수치로 대체하지 않는다.

## 관측 가능한 행동 비용의 분리 검증안

v15의 저장된 생성 Dev rollout을 검사한 결과 종료 행동(hold/handoff) 후보 117개 모두 요청 비용을 양수로 예측했다. 요청 비용은 종료 시 정확히 0이어야 하지만 평균 예측은 20.7225였고 hold의 확정 terminal cost도 평균 절대 오차 38.8397이었다(`results/l40s-tools-v16/value-cost-audit.json`). 이 사후 진단은 새로운 rollout 성능 비교가 아니다.

`/tmp/newsvendor-value-costs`에 현재 학습과 분리한 수정안을 준비했다. 공개 hold 비용과 즉시 요청 비용은 계산으로 확정하며, 모델은 불확실한 terminal loss와 이후 요청 비용을 학습한다. 종료 행동의 요청 비용 및 예산·기한상 후속 요청이 불가능한 경우의 미래 비용은 0이다. 정답 상태·응답 확률·숨긴 결과는 이 계산에 쓰지 않는다. 새로운 파라미터나 encoder 통과 없이 학습·추론·cached critic 학습에 동일한 조립 함수를 사용한다.
